# Instructions for Overgear

This directory is the Overgear sublibrary, showcase and store. Read the root `AGENTS.md`, the shared `CONSTITUTION.md`, then `overgear/CONSTITUTION.md` before changing an Overgear interface.

- All new rules specific to this store belong in `overgear/constitution/rules.js`, including navigation, catalog, checkout, empty states, merchandising and brand choices. This also applies when the request arrives at the repository root
- Use a new stable `OG`-prefixed id; do not reuse or renumber existing ids. Keep `do`, `dont`, `why`, `source`, `check` and `signals`; name a local tool when a rule is checked by a script
- Keep product-specific checks and tests under `overgear/tools/` and `overgear/tests/`. General accessibility, tokens and reusable component behavior belong to baseui; do not copy its rules here
- Do not put a store rule in `src/constitution/rules.js`, shared `AGENT_DEFAULTS`, shared component usage guidance or shared audit tools. Dependencies go from Overgear to baseui, never the other way around
- Follow the shared violation protocol, using `ConstitutionBanner` from `overgear/index.jsx` in repository sources (or `baseui-kit/overgear` in a consuming app). It understands shared ids and the local OG ids
- Edit rule sources, then run `npm run constitution` and `npm run registry`. `overgear/CONSTITUTION.md`, `overgear/AGENTS.md` and `overgear/CLAUDE.md` are generated by `overgear/tools/build/constitution.mjs`; change this generator to update these authoring instructions
- Run `npx vitest run overgear` for the product checks, and `npm test` for everything; the boundary of baseui is tested in `tests/boundary.test.js`

## The order: the checkout, the cart and the mini-cart

- The parts that these three have in common are in `overgear/example/order.jsx` (`CartLine`, `ItemLines`, `OrderSummary`, `Promo`, `PayBar`, `PayBarContent`, `OrderHead`). Change a line, the summary, the promo code row, the pay bar or the title there, once; never copy one into a surface or style it with a class of that surface
- The checkout (`cart.jsx`) is the latest base: when a surface differs from it in a shared part, the checkout is right. The cart page and the mini-cart pass their own labels and handlers (`label`, `action`, `onAction`, `pinned`), not their own markup
- "Add to cart" opens the mini-cart on a desktop and on a phone (`useAddedToCart`, the mini-cart is mounted in the shell); on a phone it is the standard `Dialog` (a sheet) with the pay bar as its footer. The mini-cart has the lines and the promo code card in its list, and the pay bar pinned at the bottom; it has no summary block
- `overgear/tools/check/order.mjs` compares the look of every shared part across the three on a desktop and on a phone, and fails when one of them drifts

## After the purchase: the orders

- The rules of the real service (og-frontend-4: orders listing, order page, payment result) are in one pure module, `overgear/example/order-core.js`, with its tests in `overgear/tests/order-core.test.mjs`. Change a status, a text, a button, a lock or the way a payment ends there, and in the tests; the pages (`orders.jsx`, `order-page.jsx`, `order-result.jsx`) only draw it
- The orders a browser starts with are `order-seed.js`: a few of every status, so each state can be seen. The way an order moves on in the demo ("What happens next") is `nextEvents` and `applyEvent`
- The page /orders, /order/:link and /checkout/result/:result are the ones of the real service; a guest buyer becomes a temporary account (`store.temp`): it has the page of its order, not a history
- `overgear/tools/check/orders.mjs` plays the list, the page of an order in every status, the buyer's flows and the way from a payment, in a browser
